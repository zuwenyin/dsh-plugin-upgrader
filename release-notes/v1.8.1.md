# 1.8.1 —— 被构建脚本卡住的那一行，现在说得出自己卡在哪

这一版修的是一个**永远修不好、还说不清为什么**的失败，外加一句描述。

## 卡在「批准构建」上的插件，重试一万次也装不上

pnpm 默认不跑依赖包的 install 脚本，除非你明确批准过。于是 `dsh-xdpool@2.6.4` 这种包：
装进去了、又被回滚、下次重试还是一样的结果。管理器其实会把这种包记进 `allowBuilds`
（写成 `set this to true or false`），这个页也一直有「批准并重启」的按钮 —— 但从来没有人
去填那一行的 `pendingBuilds`，所以按钮永远不出现。

**你能看到的后果是**：批量升级报「批量升级完成」，配一张红卡片，卡片上只有管理器的
`operation-error` 和一大片 registry 超时。没有一句话提到「批准」两个字。

现在宿主自己读 profile 的 `pnpm-workspace.yaml`（`src/host/builds.ts`，**没有新依赖**），
把还没答复的 `name@version` 精确报出来，理由从 `operation-error` 换成 `build-blocked`。
行里列出这些键和批准按钮；批量升级**跳过这些行并说明**，因为批准等于运行人家 install 时
要跑的代码 —— 这个决定必须由你来做，不能混进一个「已升级 3 个」的数字里。

## 跳过了人，就不能叫「全部已是最新」

「可升级」数字数的是所有有更新版本的行，「批量升级」只数它真能做完的行。以前这两者不一致
的时候，页面会同时显示「全部已是最新」和一个灰掉的按钮。现在有一句话解释这个差别。

## 描述里补上 `dsh-plugin`

上一版（1.7.4）把描述改成带 `DSH` 之后，`dsh-plugin` 这个词下面的名次从第 368 到了第 8。
这一版补的是同类的另一个洞：描述里一直只有空格的 `DSH plugin`，**没有连字符的
`dsh-plugin`**。它现在在，顺带把「这个插件对插件做了什么」写清楚了 —— 就地替换、不卸载、
保留启用状态。

117 → 209 个字符。npm 的搜索索引在 **255 个字符**处截断，超过的部分没有任何人索引，所以
这句话是压着上限写的，不是随便写长一点。

没有代码改动、没有测试改动、没有行为变化：这个字符串只有 npm 读。

## 顺带

- 测试 361 条，`pnpm run check` 全绿。

升级：

```bash
dsh plugin --profile web add dsh-plugin-upgrader
```
