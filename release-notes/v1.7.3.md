## 1.7.3

**一次升级里，一个包出的事不能由另一个包负责收拾。**

1.7.1 把改 profile 的动作放进了 harness 自己的写入锁，挡住的是「并发 writer 在中间读走
一份旧快照」。可锁底下那张「掉了哪个依赖」的记录，从 1.4.0 起一直是**一个 profile 一条**。
这在一次只升一个插件时没问题，在批量升级里就出事：

1. A 的 in-place 安装失败，要还原 —— 拿不到锁（另一个操作正在写 profile），还原没做成；
2. 于是退回「先卸载再装」，可那一步同样要拿锁，也没做成。**记录里还写着 A**；
3. 锁放开，批次继续跑 B。B 的 drop 顺手把这条记录**覆盖**成 B，B 装完再把它**整份清掉**；
4. 批次结束：A 从 `package.json` 里没了，下次加载时 `recoverPendingDrop` 说
   `{ kind: 'none' }` —— 没有任何东西知道 A 曾经在那里。

这不是「概率极小的竞态」，是一条确定会走到的路径：批次里一步失败不会中断后面的步骤。

**现在一条记录只属于一个包。** journal 的磁盘格式变成
`{ "version": 2, "records": [ … ] }`，每个包一条：

- `upsertRecord` 只替换同名那条，`clearRecord(dir, name)` 只结算同名那条——
  B 的 drop 不会再碰到 A 的记录，B 的确认也不会再把文件清空；
- `recoverPendingDrops(dir)` 把**所有**待办记录都修完，而不是只看第一条
  （`recoverPendingDrop` 保留成「取第一条」，只为兼容旧调用）；
- 加载时的修复日志按条报，掉了几个就报几个。

**读记录也进锁。** 以前是先读记录、再拿锁去改，中间那段空窗足以让一次修复照着**别人
已经处理完的旧记录**动手。现在锁外那次读只回答两个问题：「有没有活要干」和「拿不到锁时
该报哪些名字」；真正读、改、删全在 `package.json.lock` 里面。

**还原没做成，日志就说没做成。** `replaceWithoutRemoval` 的抛出分支以前把
`restoreDependency` 的返回值丢掉了，日志既不说成功也不说失败。现在两条失败分支都写
`the next start repairs it`——而这句话之所以现在能信，正是因为记录是按包存的：
它没被清掉，下次加载真的会补回来。

**旧文件仍然能读。** 1.7.2 及更早写的是单个对象 `{ name, spec, at }`；
`readRecords` 见到 `records` 不是数组时，把整个顶层对象当成一条记录。升级时不会因为
「格式变了」把升级中断过的 profile 判成读不懂。

**这一条写进了 `AGENTS.md` 第 23 节。** 守护用例：`test/manifest.test.ts` 5 条
（第二次 drop 不覆盖还悬着的记录、确认只结算自己那条、还原只结算自己那条、
一次恢复修完全部、旧格式仍能读），`test/install.test.ts` 1 条走真实 `runStep` 的
全链条（第一步失败 → 第二步成功 → 重新加载时把第一个依赖补回来）。

**用哨兵验过：** 把 `upsertRecord` 改回覆盖式、`clearRecord` 改回整份清空，
5 条会红（4 条 manifest + 1 条 install），实测过。

升级方式不变：

```
dsh plugin --profile web add dsh-plugin-upgrader
```
