# 1.9.2 —— 「需处理」那个数字，现在说得清它在数什么

这一版**没有代码改动**，只改了两份 README。发版是因为 npm 页面上显示的 README 来自
已发布的 tarball —— 文档不随包发出去，就等于没写。

## 数字早就有了，解释只有一行

顶部那项统计（已安装 10 / 可升级 0 / 需处理 1）从 1.7.4 起就在。但它的解释一直是两句话：
功能列表里一句「只数真的出了问题的那四种」，界面位置里一句「可以点」。够认出这个数字，
不够回答「我屏幕上这一条，到底属于哪一种、我该按哪个按钮」。

现在是一张四行的表，每行三列：**什么情况下出现**、**行上长什么样**、**你能做什么**。

| 问题 | 一句话 |
| --- | --- |
| 已装版本不兼容 | 装着的那个版本要求的 DSH 范围，现在的宿主不满足——插件很可能根本没被加载 |
| 镜像落后 | 官方源发了、你的镜像还没同步；选中了会在 pnpm 里 `ERR_PNPM_NO_MATCHING_VERSION` |
| 版本读不到 | registry 超时 / 限流、Git 或本地路径安装、包压根没发布过 |
| 构建待批准 | `allowBuilds` 里还是占位符，装到一半会失败 |

## 两种「不算进去」的，也写进去了

「最新版装不了」和「有新版本可升」都不计入这个数字。前者不是你能修好的状态，后者是好事——
任何一种算进去，这个数字就永远回不了零。这句话以前只在 `docs/rules/26-compatibility-dead-end.md`
里，现在 README 里也有了。

## 顺便承认一个自己知道的缺陷

用 `link:` / `file:` 装进来的包会拿到一句 `local path install: …` 的 `versionError`，而
`needsAttention()` 数的是「`versionError` 非空」，所以它会被算进「需处理」——点进去既没有
按钮，也没有任何可执行的动作。开发本插件时这一条永远清不掉。

这次**没有修它**，只是把它写进 README 了。理由：修它要动 `needsAttention()` 的判据（区分
「说明来源」和「真出错」），那是行为改动，不该混在一版纯文档里。写出来比让用户自己猜好。

`pnpm run check` 全绿，381 条测试一条没动（与 1.9.1 相同——这一版没碰代码）。

升级：

```bash
dsh plugin --profile web add dsh-plugin-upgrader
```
