## 1.7.0

**这一版的主题只有一句话：不该装的版本，别再让它装上去。**

插件页从 1.0 起就能换版本，但「能换」和「换了还能用」是两件事。DSH 的插件管理器会检查每个包声明的
兼容范围，不合格的安装会被宿主拒绝——听起来很安全，实际有个要命的顺序问题：**那次拒绝发生在
pnpm 已经把旧版本摘掉之后**。真实事故是这样的：把一个皮肤插件切到 `0.1.5`，它声明的是
`>=0.1.7-rc.1 <0.1.8-0`，不认当时跑着的宿主；宿主拒绝安装，包却已经从 profile 里消失，
`cordis.patch.yml` 里还留着一个指向空处的 id。用户看到的是「这个插件不见了」。

**先判断，再动手。** 现在换版本的第一步是读目标版本声明的 DSH 范围，和**正在跑的宿主**比一次，
不合格就直接回 `incompatible-version`，把「它想要的是哪个范围」一并说清楚，profile 一个字节都没动。
宿主的检查仍然是最终裁决，但不再有人先付了代价才被告诉不行。

**「正在跑的宿主」是读出来的，不是从 profile 猜的。** 这一点踩过一个坑：profile 里那份
`@deepseek-ai/dsh-app-boot` 是指进 npx 缓存的一个链接，量出来是 `0.1.2-rc.1`，而真正在跑的宿主
报 `0.2.1-rc.5`。拿 profile 去判断，会把一堆本来能装的版本标成不能装。所以版本从宿主自己的入口读。
**读不到就什么都不标**——判断权留给宿主，页面最多少一条提示，不会替你拒绝明明能装的东西。

**规则和宿主的闸门是同一套。** `engines.dsh` 在的时候它一个人说了算；不在的时候逐个检查
`peerDependencies` 里所有 `@deepseek-ai/dsh*` 的范围，`workspace:^` / `~` / `*` 都理解为「就是现在这个」，
预发布版本也算在内。范围匹配是自己实现的（`src/host/version.ts`），拿 `node-semver` 对了
49 个范围 × 41 个版本、2035 组，全部一致——对之前有 3 条不等式是错的，最明显的一条是
`~0.1.7-rc.1` 放过了 `0.1.6`。这种错**只会在你正好卡在某个 rc 边界时出现**，靠手点是发现不了的。

方向反过来同样管用：在较新的 DSH 上往回翻历史版本，不再认得当前运行时的那些版本会被标出来、
按钮变灰；在较旧的 DSH 上，如果最新版要求更高的宿主，它就不再被当作「可升级」推给你，
那一行会写清楚它想要哪个范围。

**顺带修掉一条「看起来像重启，其实是自己把自己换掉了」的失联。** 本插件升级别的插件时，
宿主会在 live profile 下重新挂载本插件自己的模块——于是你正在看的那个批次的记录，跟着旧模块一起
没了。新模块拿着一个空的表，对页面轮询的那个 id 回 `unknown-job`，页面于是说「升级进度已失去联系」，
而实际上那次安装**成功了**。现在批次状态放在 `globalThis` 上一个固定的 symbol 上，谁接话都知道这件事；
收尾也只清自己那一批，不会被上一代的实例顺手抹掉。

同一条横幅还有另一个来源：宿主是单线程的，pnpm 安装期间一次轮询超时或 5xx 本来就很正常，而过去
**一次没答上来**就判定「进度失联」。现在连续四次没答上来、约 3 秒真正静默才会放弃，中间只要成功一次
就清零。另外「卡住了」原来只有一句话，现在分清两种：pid 一直没变（旧进程还在答话）和 pid 变了但页面
加载不进新宿主，这两种需要的动作不一样。

**换版本失败时，恢复要看清楚「坏成了什么样」再动手。** 包还在盘上 → 重新选中它；包已经没了 →
把上一个版本装回来。结果里带 `rolledBack`，日志能说清到底装回了什么；连回滚本身都被拒绝时，
它会直接说被拒绝，而不是在一堆更糟的情况上写一句「失败」。

安装命令没变：

```bash
dsh plugin --profile web add dsh-plugin-upgrader
```
