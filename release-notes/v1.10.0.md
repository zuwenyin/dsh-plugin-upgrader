# 1.10.0 —— 多选卸载：本页第一个没有撤销的动作

这个插件一直在给「插件」页补 DSH 自带页缺的东西。卸载不在这个名单里——自带页本来就能卸一个。
缺的是**批量**卸载，而批量升级早就在这里了。

## 为什么这个功能需要多想一层

这个插件的招牌是**可逆**：升级不卸载、启用状态保留、失败回滚、历史版本随时退回去。
卸载是它做的第一件不可逆的事——包能装回来，但配置和数据不会跟着回来，历史版本也没有了。

所以它没有被做成第二个「主按钮」：

- 按钮是**描边危险色**，不是实心 primary。它永远不是页面上最显眼的那一下。
- 点它不是立刻执行，而是先打开确认框，把**每一个**要卸的插件名列出来。
- 确认框里写明「卸载没有回滚」「插件留在磁盘上的配置和数据不会被删」。

## 三个不能混的说法

宿主会拒绝卸载，理由有三种，页面上不能都写成「失败」：

| 宿主返回 | 意思 | 页面怎么说 |
| --- | --- | --- |
| `not-removable` | 这东西本来就不归你删（内置插件、被其它层拥有的行） | 立刻拒绝，连 pnpm 都不启动 |
| `stop-profile` | 这台宿主没有热更新，而这个包由 profile 启动，**重启也解不开** | 说清重启没用，指向 DSH 自带「已安装」页那条真能走的路 |
| `bundle-in-use` | 加载器还持着它的 fiber | 先自己解一次扣再重试，仍失败才说重启 |

## 它为什么是独立入口

升级那条流水线的承诺是「结束时那个版本在盘上」，所以它写满了「把装坏的东西装回去」——
结果里带 error 就进恢复，包还在盘上就重新选中，包已经没了就按旧版本重装。

对升级这是对的，对卸载**正好是反的**：一次被拒绝的卸载会悄悄把用户刚要求删掉的包装回来。

所以卸载走 `removeStep`，一条规则：要么删掉，要么说清为什么没删，**永远不安装任何东西**。
它只复用了其中一段早就存在的逻辑（`bundle-in-use` 的自解）。它也不碰 profile 的
`package.json` 和 journal——那套补丁机制是给 in-place 替换用的，纯卸载走宿主自己的
`removeBundle`，那才是管理器真正的卸载入口。

## 两条一直没动的边界

- **本插件自己不参与批量卸载**，理由和批量升级一样：卸掉正在跑这批任务的代码，就没人收尾了。
- **`removable === false` 的行勾不上**：内置插件、被其它层拥有的行。这不是前端猜的，
  是 manager 自己给的答案。

## 卸载的进度不再说「正在下载并安装」

pnpm 删包时会先校验 lockfile，而「lockfile 校验通过」这一行在升级流程里代表「开始安装」，
所以第一版的进度面板把卸载也叫成「正在下载并安装」，慢的时候还在解释「首次安装会比较慢」。

现在宿主单独告诉页面这一步是什么动词，页面把「动词 + 阶段」合起来取文案：卸载说「正在卸载」，
也有一句属于自己的慢提示；真的同义的阶段（写入配置、取消、校验依赖）仍然共用。
认不出动词时（例如接管了一个老宿主留下的任务）保持原来的安装说法——猜成「卸载」错得更离谱。

## 怎么验证

`test/remove-step.test.ts` 13 条，覆盖上面每一格。其中两条专门守着「不装回来」：
「一次卸载把包拿走且什么也没安装」和「宿主不肯放手的包被报出来，而不是被卸掉」。
把 `removeStep` 临时改成走 `runStep` 过一遍，前者立刻变红——这条测试真的是在守门，不是摆设。

`test/job-panel.test.ts` 另外 4 条守文案：卸载不会被叫成安装、同义阶段仍然共用、
没有动词时保持安装说法。把动词判断临时关掉，这几条会红。

400 tests.
