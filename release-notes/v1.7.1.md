## 1.7.1

**一个关着的插件，升级失败之后自己打开了。**

这是 PR #2（HootRock）报的问题，也确实能在这份代码上复现：用户把某个插件关掉，点升级，
升级失败，回来一看插件在跑。

根因不在安装，在恢复。换版本必须先卸载，所以 `runStep` 的顺序是
「先直接 install → 被 `already-installed` 拒绝 → 就地替换 / 退回卸载再装」。
一旦走到「卸载之后再装」这条路又失败了，`recover()` 就要负责收尾：包还在盘上就把它选回去，
包已经没了就把旧版本装回来。问题出在前一半——它调的是 `restoreSelection()`，而这个函数
名字没有骗人：它**只会** `setBundleEnabled(name, true)`。

本来成功路径上那句 `restoreEnabledState(..., step.enabled)` 会按「这一步想要什么」对齐，
但它在 `installed` 为假时被跳过——也就是失败的时候跳过。于是失败的窗口里，
**唯一**发生的修复动作就是「打开它」。

**现在按「这一步想要什么」修，不按「盘上有什么」修。** 包还在盘上只说明不用重装，
说明不了它该不该跑。`step.enabled === false`（用户明确要求关着）时改走
`restoreEnabledState(manager, step, false, log)`：读到已经关着就什么都不做，读到还开着就关下去。

两种失败形状同时修好，因为它们走的是同一个 `recover()`：manager 返回错误
（`result.error`）和 `installBundle` 直接抛出（pnpm 死了）都覆盖。

**没带这个字段的调用方，行为一个字都没变。** 只有明确的 `=== false` 才改道，
`undefined` 仍然等于「保持加载」——老客户端、脚本、还有此前所有不带 `enabled` 的调用
都按原来的答案走（「失败的替换不许把插件丢在未加载状态」）。这和 `runStep` 用
`typeof step.enabled === 'boolean'` 决定要不要把 `enabled` 交给 manager 是同一条约定。

**就地替换那条路从来没受影响。** `replaceWithoutRemoval` 成功之后走的是
`restoreEnabledState(..., options.enabled)`，本来就是按目标状态对齐的。这个 bug 只住在
「卸载之后又失败」这一条路上——也就是最不容易被点到、但一旦点到就把用户设置改掉的那条。

**这一条写进了 `AGENTS.md` 第 21 节。** 五个新用例钉住它：关着的不许被打开、
抛出和返回错误两种形状、明确要加载的仍然会被选回来、已经开着的不做多余切换、
以及目标状态优先于当前状态（manager 报它还在加载时，要关下去而不是留着）。
把 `recover` 里那行改回无条件 `restoreSelection`，其中三条会红——实测过。
