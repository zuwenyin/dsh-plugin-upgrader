## 1.3.0

**一次批量升级不再把下一次启动变成启动错误弹窗。**

桌面壳只在宿主启动时快照一次注入表，之后每个文档都复用它。那张表落在 boot manifest 里，
里面的 batch URL 带一个 revision 哈希，而宿主只保留当前这一代和上一代。一次替换两个或更多
插件的升级会把这个哈希翻两次，于是壳手里的表指向宿主已经丢弃的批次——取回来是 404，
整批条目全部激活失败，壳弹出 `web boot: N entries did not activate`，盖在一个一秒钟前
还好好的页面上。插件没有办法重建那张表，而重新启动总是从新的表开始，所以这个弹窗看起来
毫无道理。

让它变容易触发的是一件事：替换主题插件后，页签会自己重载页面去找回主题的样式表，而那次
重载可能正好落在死掉的表上。现在重载前会先问宿主——对每个 boot 批次发一个 `HEAD`——确认
批次已经不在时说「需要重启」，而不是一头撞进致命错误。拿不到确定答案（连接被拒、500）
不算结论，所以一次网络抖动永远不会把一次正常的重载变成拒绝。

**落后于上游的镜像不再看起来像是「已经是最新」。** 版本列表读的是 profile 实际安装所用的
registry，而镜像落后于它复制的源，有时落后几小时。这个落后在镜像自己的文档里是看不见的：
它只是不列那个新版本，于是那一行显示一个较旧的 `latest`，没有任何迹象提示少了东西。这件事
重要是因为配置的 registry 上没有的版本**根本装不了**——pnpm 通过它解析并以
`ERR_PNPM_NO_MATCHING_VERSION` 失败，把整条命令拖垮，同批无关的包一起算。现在每一行还会
向上游问一次「已安装版本之上、而这个镜像没有」的版本并列出它们，于是「有新版本，你的镜像
还没跟上」和「无事可做」读起来是两件事。
