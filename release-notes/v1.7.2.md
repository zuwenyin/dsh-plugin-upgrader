## 1.7.2

**慢的时候，面板要说的是真话。**

这一条来自一次真实降级：把 `@linxin666/dsh-pet` 从 0.4.14 降回 0.1.18，那次升级**其实成功了**
（1/1 完成，0 失败，`ok: true`，pnpm 报 `Done in 2m 14.2s`）。可面板整整两分钟写着
「正在下载并安装」，还挂着「状态已停止更新，请检查更新」，而同一时刻日志里 pnpm 正在
逐条核对锁文件：

```
? Verifying lockfile against supply-chain policies (91 entries)...
[WARN] GET https://registry.npmmirror.com/@jimp%2fplugin-contain error (ETIMEDOUT). Will retry in 1 minute. 1 retries left.
[WARN] GET https://registry.npmmirror.com/@jimp%2futils error (ETIMEDOUT). Will retry in 1 minute. 1 retries left.
...
✓ Lockfile passes supply-chain policies (91 entries in 2m 13.6s)
```

用户看到的是一个卡住然后坏了的升级，实际上是一次两分多钟的健康安装。**两个都是假象。**

**第一个假象：阶段说错了。**

根因在宿主上报阶段的方式：`dsh-plugin-manager` 是**先** `announce('installing')`、
**再** `runPnpm(...)` 的。也就是说 manager 说的 `installing` 其实是「pnpm 起来了」，
不是「已经过了校验」。而我们这边的阶段判定把 `installing` 当成终点钉住了，
于是 pnpm 后来才打印的校验行**改不动**它——整个校验过程都显示成「正在下载并安装」。

**现在按 pnpm 自己的话判阶段。** 校验开始（`? Verifying lockfile …`）就是 `verifying`
（正在校验依赖锁文件），哪怕 manager 已经说过 `installing`；一直到 pnpm 给出结论
（`✓ Lockfile passes supply-chain policies` / `✗ Lockfile failed supply-chain policy check`）
才回到 `installing`。校验期间 pnpm 还会打印重试和进度计数，所以中途的普通行**不能**
提前结束它。

开始行和结论行都含 "supply-chain policies" 这几个字——**只**匹配这个词是分不出开始和结论的，
所以开始行认 `/verifying lockfile/i`，结论行认 `/lockfile.*passes supply-chain policies/i`
和 `/lockfile.*failed supply-chain policy check/i`。

**`applying` 和 `cancelling` 仍然不会被后续日志回退。** 它们是 manager 的最后一句话，
比 pnpm 的输出更具体。

**第二个假象：「状态已停止更新」误报。**

面板原来判定停滞的方式是「二十秒内没看到**不一样**的快照」。可快照里的 `activity`
来自 pnpm 的输出——pnpm 重试的时候一分钟不打印一行，这很正常。于是健康的升级被判成停滞。

**现在问宿主，不问 pnpm。** 宿主每 2 秒重新盖一次心跳（`job.heartbeatAt`），
只要还在处理这一批就一直往前走；面板用心跳判定活性，宿主在 overview 和 job 两个
响应里都报这个值。二十秒的阈值和那句话都没变：**宿主真的不说话了，它还是会说。**

**这一条写进了 `AGENTS.md` 第 7 节。** 新的守护用例：`test/progress.test.ts`（8 条，
新增「manager 说过 installing 之后开始的校验仍然被命名」「校验一直保持到 pnpm 给出结论」
「校验失败不许被打扮成安装」）、`test/job-panel.test.ts`（5 条，心跳在指纹里、
宿主有心跳就不算停滞、宿主不说话了才算）、`test/job-store.test.ts`（走真实路由，
断言 job 响应里带心跳）。

**用哨兵验过：** 把 `installing` 重新钉住，两条会红；去掉「校验保持到结论」，
一条会红——都实测过。
