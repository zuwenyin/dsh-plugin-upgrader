## 1.4.0

**一次失败的升级再也不能让 profile 缺一条依赖。** 就地换版本的原理是把包名那条依赖从
`profile/package.json` 里删掉，让管理器的 `already-installed` 守卫不再触发，再由 pnpm 把
新版本写回去。如果进程在这个窗口里死掉——重启、崩溃、pnpm 被杀——磁盘上没有任何东西记得
那条依赖，包还在磁盘上却对管理器不可见。主题插件就是这样被升级掉的：依赖条目再也没回来，
下一次 `pnpm install` 把那个孤儿目录挪进 `node_modules/.ignored`，此后这个插件既不能升级、
也不能卸载，甚至看不见，除非手工去改 JSON。

现在这个意图会在条目离开 manifest **之前**写进 `package.json.upgrader-journal.json`，并且
本插件每次加载都会修复它找到的记录：条目仍然缺失就按原来的版本范围补回去，pnpm 真的写成了
就结案并清掉记录。恢复是尽力而为的，从不作为前置条件——一个修不好的 profile 仍然能加载这个
页签，因为那是唯一能修它的入口。

**面板现在会说 pnpm 在做什么，而不是杵着一个不动的标签。** 校验 lockfile 是冷 profile 上
最长、也最不自我解释的阶段：它打一行字，然后几分钟什么都不打，页签就一直停在「准备中」。
这个阶段现在有名字了（「正在校验依赖锁文件」），并且最新一行 pnpm 输出就显示在它旁边——
registry 超时和下载在以前都读作「正在安装」，而只有其中一种意味着继续等。停滞检测也把那
一行算进去，所以一个一直在打字的步骤不再被判为停滞。

**写入锁超时现在会解释自己。** harness 用 `package.json.lock` 串行化
`profile/package.json` 的写入者，而共享的 `atomic-write` 给一个不说预算的调用者 2 秒。
当一次升级跑得够久、另一个写入者握住了那把锁时，页签报的是
`atomic-write: timed out waiting for the writer lock at …package.json.lock`——一个文件名和
一个 pid，看着页签的人无法据此做任何事。现在这句话前面先说清它是什么意思、该怎么办：
另一个操作正在改写 manifest（等它结束），或者锁被一次被杀掉的升级永远留在了那里（重启 DSH
会清掉）。原句保留在方括号里，因为那是要在日志里搜索的字符串。
